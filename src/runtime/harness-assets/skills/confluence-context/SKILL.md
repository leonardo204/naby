# confluence-context — 언제 사내 문서를 조사할지 판단

당신은 이 스킬을 통해 **"지금 질의가 사내 Confluence 문서를 필요로 하는가"** 를 판단한다.
필요하다고 판단하면 **직접 답하지 말고** `confluence-researcher` 서브에이전트에 조사를 위임하고, 반환된 **압축 결과만** 활용한다.

이 스킬은 판단 로직만 보유한다(경량). 실제 검색·인출·컨텍스트 격리는 서브에이전트가 전담한다(설계서 5장).

## 1. 발동 판단 (설계서 5.1)

### 발동한다
- 사내 **고유 용어·서비스명·내부 약칭**의 의미/사양을 물을 때 (예: "PAY 게이트웨이가 뭐야", "그 서비스 왜 그렇게 동작해").
- **내부 정책·규약·표준·절차**를 물을 때 (배포 정책, 코드 규약, 보안 규정 등).
- **ADR·설계 결정·런북·장애 대응 절차**의 근거를 물을 때.
- **팀 관행**(리뷰 프로세스, 온콜, 릴리스 흐름)을 물을 때.
- 사내 **에러코드·티켓 키·상수명**의 배경을 물을 때.
- 코드/파일만으로는 "왜 이렇게 되어 있는지"의 근거가 안 나오고, 그 근거가 문서에 있을 법할 때.

### 발동하지 않는다
- 일반 프로그래밍 지식(언어 문법, 표준 라이브러리, 알고리즘)으로 답할 수 있을 때.
- **이미 열린 파일/컨텍스트에서 해결 가능**한 사안.
- 단순 리팩터링·포맷팅·기계적 수정.
- 근거: 매 턴 검색은 그 자체가 토큰 낭비다(설계서 5.1). 애매하면 발동하지 않는 쪽을 기본값으로 둔다.

### confluence.yml 해석 규칙 (spaces 파싱)
`confluence.yml`의 `spaces` 는 항목마다 두 형태를 허용한다. 조사 위임 전에 각 항목을 아래처럼 해석한다.

| 형태 | 예 | 해석 |
|---|---|---|
| 문자열 | `KT` | 스페이스 키 = `KT`, `under` 없음 → **스페이스 전체** 참조 |
| 매핑 | `{key: PAY, under: "123456"}` | 스페이스 키 = `PAY`, 하위 트리 범위 = 페이지 id `123456` → 그 페이지 + 하위만 참조 |

- 매핑의 `under` 값이 **페이지 URL**이면(`.../pages/<id>/...`) `/pages/` 다음의 `<id>` 를 추출해 페이지 id로 쓴다. 예: `.../wiki/spaces/PAY/pages/123456/Some-Title` → `123456`.
- `under` 는 **색인 범위가 아니라 참조(검색) 범위**만 좁히는 필터다 — 색인은 스페이스 전량을 유지한다(설계서 6.3①).

### 발동 시 절차
1. (이 프로젝트에서 처음이라면) 아래 **2. 설치 도우미**를 먼저 수행한다.
2. `confluence-researcher` 서브에이전트를 호출해 조사시킨다. 질의 요지 + 관련 스페이스 힌트를 전달한다. 해당 스페이스가 `under`(하위 트리 범위)를 가진 매핑 형태이면, 그 **`under` 페이지 id 를 서브에이전트에 함께 전달**해 `find_docs(intent, space, k, under=<id>)` 로 검색하게 한다. 전체 스페이스면 `under` 없이 위임한다.
3. 서브에이전트가 반환한 **압축 결과(결론·근거·정확용어·한계 + 피드백 핸들)** 만 사용한다. 중간 산출물은 요구하지 않는다.
4. 반환된 **피드백 핸들**로 **아래 3. rating 흐름**을 수행한다(메인이 `submit_feedback` 호출). 조사·인출은 서브에이전트가 하지만, rating은 **메인 컨텍스트의 개발자만** 줄 수 있으므로 이 단계는 메인/스킬의 몫이다(설계서 6.8.1).
5. CIC가 응답하지 않으면 조사를 포기하고 **일반 지식으로 작업을 계속한다**(작업 흐름 차단 금지, 설계서 9.5).

## 2. 최초 발동 시 설치 도우미 (설계서 9.3 / 9.4)

설치는 별도 실행 단계가 아니라 **스킬 최초 발동 시점에 인라인으로** 수행한다. 절차를 짧게 유지하고, 실패 시 즉시 일반 작업으로 넘어간다.

### 2.0 멱등성 게이트 (가장 먼저)
- `.naby/confluence.yml` 이 **이미 존재하면 설치 도우미를 발동하지 않는다.** 곧바로 "1. 발동 시 절차"의 조사로 진행한다(설계서 9.5).
- 부재할 때만 아래 1~5단계를 수행한다. 범위 변경은 `confluence.yml` 직접 편집 또는 명시적 재실행 요청으로만 한다.

### 2.1 1단계 — CIC 연동 검증
naby에서 `cic` 서버는 **설정 → System MCP의 내장 프리셋**이다. `.mcp.json` 도 `.env.local` 도 쓰지 않고, 주소(`https://skills.altimedia.com/cic/mcp`)와 `Authorization: Bearer` 헤더는 제품이 안다 — 사용자가 넣는 값은 토큰 하나다. 그래서 검증도 **두 가지**로 줄어든다. **①만 보고 성공 처리하지 않는다** — 연결은 되었으나 색인이 없어 결과가 비는 상태가 가장 흔한 실패다.

| 검증 | 방법 | 실패 시 안내 |
|---|---|---|
| ① 도구 표면 | 이 턴의 도구 목록에 **`cic__find_docs`·`cic__read_section` 존재** 확인 | 설정 → System MCP에서 cic 토큰 저장·테스트 안내 |
| ② 실질 질의 | 고정 질의(예: `find_docs(intent="설치 확인용 핑", k=1)`)로 호출해 **카드 응답 형식** 확인 | 색인(P2) 미구축·DB 연결 이상 안내 |

- 둘 중 하나라도 실패하면 → **조사를 포기하고 일반 작업으로 즉시 진행**한다. 사용자에게 한 줄로 사유만 알린다. 작업을 막지 않는다(설계서 9.5).
- 토큰은 naby가 MCP 엔트리에 저장하고 화면으로 되돌려주지 않는다. 토큰 값을 파일에 적거나 대화에 복사하지 않는다(자격증명 유출 방지, 설계서 9.5).
- cic 프리셋이 아직 저장되지 않았으면 도구 호출 자체가 불가능하다. 이때는 조사를 시도하지 말고 **설정에서 cic 토큰을 저장해야 한다는 사실만** 알린다.

### 2.2 2단계 — 스페이스 목록 제시
- CIC가 서비스 계정 권한으로 조회 가능한 스페이스 목록을 제시한다. **지정 판단에 필요한 정보만** 부기한다.

| 부기 항목 | 목적 |
|---|---|
| 스페이스 키 · 명칭 | 식별 |
| 페이지 수 | 색인 규모·초기 소요 시간 판단 |
| 최근 갱신일 | 활성 스페이스 여부 판단 |

- **후보 추천·자동 선택을 하지 않는다.** 목록 제시에 그친다(설계서 9.1 — 스페이스는 사용자가 지정).
- 목록 조회 권한이 없으면(설계서 12장 미결) 이 단계를 생략하고 3단계의 **URL 입력 방식만** 제공한다.

### 2.3 3단계 — 사용자 지정
사용자는 둘 중 하나로 지정한다.

| 방식 | 내용 |
|---|---|
| 목록 선택 | 2단계 목록에서 직접 선택 |
| URL 입력 | Confluence 페이지 URL을 붙여넣으면 **스페이스 키를 파싱**하여 지정(스페이스 키를 모를 때). 예: `.../wiki/spaces/PAY/pages/123` → `PAY` |

- **하위 트리 한정 옵션**: 사용자가 스페이스 전체가 아니라 **"특정 페이지 하위만"** 참조하길 원하면, 그 페이지의 URL 또는 페이지 id 를 받아 `under` 로 기록한다(아래 2.5). URL이면 `.../pages/<id>/...` 에서 `<id>` 를 추출한다. **기본값은 스페이스 전체**이므로, 하위 트리 한정을 명시하지 않으면 문자열 형태로 기록한다.

### 2.4 4단계 — 지정 결과 확인 (규모·권한 경고)
- 지정된 스페이스의 **총 페이지 수 + 초기 색인 예상 소요 시간**을 표기한다.
- **권한 경고**(설계서 10.3): "이 스페이스는 팀 전원이 이미 열람 가능한가?"를 확인시킨다. 서비스 계정이 읽을 수 있는 문서는 CIC 사용자 전원에게 검색 결과로 노출될 수 있다(설계서 10.2). 인사·재무 등 접근 제한 스페이스는 지정 대상에서 제외하도록 안내한다.
- 사용자 확인 후에만 5단계로 진행한다.

### 2.5 5단계 — 기록 및 색인 등록
- `.naby/confluence.yml` 에 **`spaces` 만** 기록한다(naby는 하네스 자산을 벤더 디렉터리가 아니라 자기 홈에 둔다). 순위 가중치·감점 항목은 기록하지 않는다(시스템이 산출, 설계서 6.2). 형식:
  ```yaml
  spaces:
    - ARCH                    # 스페이스 전체 (문자열 형태)
    - key: PAY                # PAY 스페이스 중
      under: "123456"         # 이 페이지 + 하위만 참조 (페이지 id 또는 URL)
  ```
  - 하위 트리 한정이 없는 스페이스는 **문자열**로, "특정 페이지 하위만"을 원한 스페이스는 **`{key, under}` 매핑**으로 기록한다. `under` 는 색인이 아니라 참조 범위만 좁힌다(색인은 스페이스 전량 유지, 설계서 6.3①). URL을 받았으면 `/pages/<id>/` 에서 페이지 id 를 추출해 기록한다.
- 지정한 스페이스를 **CIC에 등록**한다. 워크스페이스는 공유 자원이므로(설계서 4장):
  - **이미 색인된 스페이스** → 등록만 수행. 재색인하지 않음 → 즉시 조사 가능.
  - **미색인 스페이스** → 색인 큐에 등록. **색인 진행 중에도 스킬은 정지하지 않고** `search_cql` 예비 경로로 조사를 수행한다(설계서 9.4 5단계 / 6.3 ③).
- 기록·등록이 끝나면 그대로 "1. 발동 시 절차"의 조사로 이어간다.

## 3. rating 흐름 — 피드백 핸들로 submit_feedback (설계서 6.8.1 / `cic-mcp-tools` §2.5)

`confluence-researcher`가 반환한 압축 결과 끝에는 **피드백 핸들**이 실려 있다:

```yaml
query_id: <최종 채택 검색의 find_docs query_id — 없으면 null>
answer_page_ids: [<근거로 인용한 카드 page_id …>]
read_page_ids: [<실제 read_section/read_page 한 page_id …>]
```

**컨텍스트 격리**로 `find_docs`의 `query_id`·카드는 서브에이전트 안에서 소멸한다. 따라서 rating은 이 핸들을 받은 **메인/스킬만** 상관·호출할 수 있다. 도구는 `submit_feedback(query_id, helpful, page_ids?, note?)` — naby의 도구 목록에는 `cic__submit_feedback`(Claude Code 표기로는 `mcp__cic__submit_feedback`)으로 뜨며, **cic 서버가 자동 노출하는 메인 도구 표면**이고 서브에이전트 tool 목록에는 없다(설계서 6.8.1 / §2.5).

### 3.1 언제 호출하는가 — 비차단·저마찰 (설계서 9.5 / 6.8.5)
rating은 **선택**이다. 개발자에게 별점을 캐묻지 않는다. 자연스러운 시점에만, 조용히 호출한다.

| 시점 | 신호 | 호출 |
|---|---|---|
| **명시적 유용** | 개발자가 답변을 채택/수긍(예: "그게 맞네", 그대로 반영) | `submit_feedback(query_id, helpful=true, page_ids=answer_page_ids, note?)` |
| **명시적 무용** | 개발자가 "쓸모없었다"/"틀렸다"/"그거 아니야"를 표함 | `submit_feedback(query_id, helpful=false, page_ids=answer_page_ids, note="개발자 불만 요지")` |
| **암묵적 인출** | 명시 반응이 없을 때 — 조사가 실제로 문서를 인출했으면 | `submit_feedback(query_id, helpful=true, page_ids=read_page_ids)` (인출 자체가 약한 긍정 신호, 설계서 6.8.2) |

- `query_id`가 `null`이면(색인 우회·`search_cql` 전용) 상관 키가 없으므로 `submit_feedback`을 호출하지 않는다. 조사 결과만 사용한다.
- 명시 반응이 없고 인출도 없으면(근거 없음 반환 등) 호출을 생략한다. **무리한 rating 유도 금지** — 개발자에게 과한 질문을 던지지 않는다(설계서 9.5).
- 호출은 **비차단**: `submit_feedback`이 실패하거나 응답하지 않아도 개발자의 원래 작업을 지연시키지 않는다. 조용히 넘어간다.

### 3.2 부정 경로 — 확신-오답 gap 신호 (설계서 6.8.3)
개발자가 그럴듯한 답을 받고도 "쓸모없었다"를 표하면, 이는 **top-5에 고점수 오답이 떠서 채택됐으나 실제 정답은 밖**인 gap의 유일한 관측 창이다(어떤 자동 신호에도 안 걸림). 이때는 반드시 `helpful=false`로 `submit_feedback`을 호출해 확신-오답 gap 신호를 적재한다. `note`에 개발자 불만의 요지를 짧게 담으면 후속 검토에 도움이 된다.

## 4. 원칙

- **직접 검색하지 않는다.** 조사는 반드시 `confluence-researcher` 서브에이전트에 위임한다(컨텍스트 격리, 설계서 5.2).
- **작업 흐름을 막지 않는다.** CIC 미도달·미승인·색인 미구축 어느 경우에도 사용자의 원래 작업을 지연시키지 않는다(설계서 9.5).
- **멱등**: `confluence.yml` 이 있으면 설치 도우미를 재발동하지 않는다.
- **최소 발동**: 애매하면 발동하지 않는다. 사내 문서 없이 답할 수 있으면 그렇게 한다.
- **권한 우선**: 스페이스 지정 시 열람 경계를 항상 확인시킨다(설계서 10.3).
