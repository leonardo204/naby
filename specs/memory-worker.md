# 기억 작업 세션

> 이 문서가 답하는 질문 — **"기억 작업이 사용자의 구독 모델을 쓰는데, 어떻게 사용자 요청을 느리게 하지 않는가?"**

## 0. 배경

2026-11-10 사용자 요청. 기억 작업은 사용자 세션과 별개인 숨은 세션에서 돌고, 설정에서 돌고 있는지와 무엇을 하는지 볼 수 있어야 한다. 사용자의 요청은 나비의 작업 때문에 늦어지면 안 된다.

지금은 코드 흐름은 막지 않지만 같은 시간에 겹친다.

- **회고 스윕**은 사용자 턴이 **시작될 때** 백그라운드로 출발한다. 그 안의 판정·검수·정리·요약 호출이 사용자 턴과 같은 시간에 같은 구독으로 돈다.
- **턴 뒤 검수와 요약**은 턴이 끝나면 출발한다. 사용자가 바로 다음 말을 보내면 겹친다.
- 구독(Claude Agent SDK) 호출은 매번 CLI 프로세스를 하나 띄운다. 겹치면 구독의 동시 사용 한도와 이 컴퓨터의 자원을 사용자 턴과 나눠 쓴다.

## 1. 병렬로 돌리되 떼어 놓는다

기억 작업은 사용자 턴과 **동시에** 돈다. 쉬는 시간을 기다리지 않는다. 사용자 턴이 늦어지는 길은 세 가지이고, 각각을 막는다.

| 늦어지는 길 | 지금 | 막는 방법 |
|---|---|---|
| 서버의 이벤트 루프 | 기억 작업의 DB 조회·쓰기(`node:sqlite`, 동기)가 사용자 턴의 스트리밍과 같은 루프에서 돈다 | 기억 작업을 **별도 프로세스**로 옮긴다(R1) |
| DB 쓰기 잠금 | 연결이 하나뿐이다. 두 번째 연결이 생기면 잠금 대기 설정(`busy_timeout`)이 없어 바로 실패한다 | 연결마다 `busy_timeout`을 두고, 기억 쪽 쓰기는 짧은 트랜잭션으로 나눈다(R3) |
| 컴퓨터 자원 | 기억 호출도 CLI 프로세스를 띄워 같은 CPU를 쓴다 | 기억 프로세스와 그 자식의 우선순위를 낮춘다(R4) |

- **R1 별도 프로세스.** 기억 작업 세션은 앱 서버와 다른 Node 프로세스(Electron `utilityProcess` 또는 `child_process.fork`)에서 돈다. 자기 이벤트 루프와 자기 DB 연결을 갖는다. 서버는 작업을 넘기고 상태를 받기만 한다. 서버가 하는 일은 메시지 한 통이라 사용자 턴에 영향이 없다.
- **R2 대기열과 동시 호출 수.** 회고 판정, 턴 뒤 검수, 정리 패스, 요약, 단계 승격, 보관·삭제가 모두 이 대기열을 거친다. 모델 호출은 동시에 **하나**만 한다. 사용자 턴과는 겹쳐도 된다.
- **R3 DB 동시성.** DB는 이미 WAL 모드라 읽기와 쓰기가 서로 막지 않는다. 연결마다 `busy_timeout`(5초)을 둔다. 기억 쪽 쓰기는 기억 수십 개 단위로 나눠 커밋해서, 사용자 턴의 쓰기가 오래 기다리지 않게 한다.
- **R4 낮은 우선순위.** 기억 프로세스와 그것이 띄우는 CLI 프로세스는 OS 우선순위를 낮춘다(macOS·Linux `nice`, Windows below-normal). CPU가 바쁠 때 사용자 턴이 먼저 돈다.
- **R5 구독이 막히면 물러선다.** 모델 호출이 사용량 한도나 과부하(429·529)로 실패하면 기억 작업은 그 작업을 뒤로 미루고 점점 길게 기다린다(1분부터 최대 30분). 사용자 턴과 한도를 다투며 재시도하지 않는다.
- **R6 세션 모델을 쓴다.** 작업마다 그 작업을 만든 턴의 모델 정보를 함께 담는다(memory-auto-apply R38).
- **R7 사용자 화면에는 없다.** 기억 작업 세션은 채팅 세션이 아니다. `sessions` 테이블에 행을 만들지 않고, 사이드바·탭·최근 목록에 나오지 않는다. 대화 기록도 남기지 않는다.
- **R8 재시작.** 대기열은 저장하지 않는다. 앱을 다시 켜면 검수 대기 기억, 요약 없는 긴 기억, 정리·보관 대상으로 대기열을 다시 채운다. 기억 프로세스가 죽으면 서버가 다시 띄운다.
- **R9 회고는 턴 시작에서 떼어 낸다.** 지금은 사용자 턴이 시작될 때 회고가 출발한다. 앞으로는 서버가 "턴이 시작됨"만 알리고, 회고는 기억 프로세스가 돌린다.

## 1a. 구현에서 정한 것 (0.3.0)

- **R1a 프로세스.** `child_process.fork`로 `shell/dist/memoryWorker.mjs`를 띄운다. 이 코드는 Next 서버 안에서 돌아 `electron`을 불러올 수 없으므로 `utilityProcess`를 쓰지 않는다. Electron 아래에서는 `ELECTRON_RUN_AS_NODE=1`로 띄운다. 두 번 연속 시작에 실패하거나 1분 안에 5번 죽으면 기억 작업을 서버 안에서 돌리고 로그를 남긴다. 기억이 조용히 멈추지 않게 한다.
- **R1b API 키 호출은 서버가 한다.** API 키와 ChatGPT 로그인 정보는 프로세스 경계를 넘기지 않는다는 기존 규칙에 따라, 그 호출은 기억 프로세스가 서버에 맡긴다. Claude 구독 호출(CLI를 띄우는 것)은 기억 프로세스에서 낮은 우선순위로 돈다. DB 작업은 모두 기억 프로세스가 한다.
- **R2a 종류마다 대기 작업 하나.** 같은 종류의 작업이 또 들어오면 기다리는 작업에 합친다. 설정에는 DB에 남은 일의 양을 함께 보인다(100개가 넘으면 "100+").
- **R5a 한도에 걸리면 모델 호출 전체를 멈춘다.** 한도는 모든 기억 작업이 나눠 쓰므로 걸린 작업만 미루지 않는다.
- **R8a 재시작 뒤 첫 턴을 기다린다.** 다시 채운 작업은 어느 모델로 돌지 정해 줄 턴이 올 때까지 "대기"로 보인다(memory-auto-apply R38).
- **회고의 후속 작업.** 회고는 끝에서 검수·정리·요약을 직접 돌리지 않고 각각 작업으로 대기열에 넣는다.

## 2. 설정에서 보이는 것

설정 → 기억에 "기억 작업" 줄을 둔다. 펼치면 다음을 보인다.

- **상태:** 쉬는 중 · 작업 중 · 사용자 요청이 끝나길 기다리는 중
- **지금 하는 일:** 예) "새 기억 3개 검수 중", "기억 20개 요약 중"
- **대기 중인 작업 수**와 종류별 개수
- **최근 완료:** 시각, 작업, 결과 한 줄("2개 적용 · 1개 정리")
- **최근 실패:** 시각과 이유("모델을 부를 수 없음" 등)
- **쓰는 모델**과 오늘 부른 횟수

화면을 열어 둔 동안 몇 초마다 새로 읽는다. 기억의 내용은 보이지 않는다(활동 로그와 같은 원칙).

## 3. 바꾸지 않는 것

- 각 작업의 판정 규칙과 프롬프트.
- 기억의 쓰기는 지금처럼 턴 안에서 바로 일어난다. 대기열을 거치는 것은 쓰기 이후의 검수·정리·요약뿐이다.
- 구독 사용량은 줄지 않는다. 기억 호출도 사용자의 구독 한도(5시간 사용량 등)를 함께 쓴다.

## 4. 검증

- mock 모델이 일부러 느리게 답하는 기억 작업을 돌리면서 사용자 턴을 보내, 사용자 턴의 첫 응답 시간이 기억 작업이 없을 때와 같은지 잰다.
- 두 연결이 동시에 쓸 때 `SQLITE_BUSY` 없이 끝나는지 확인한다.
- 기억 프로세스를 강제로 죽였을 때 서버가 다시 띄우고 대기열을 다시 채우는지 확인한다.
- 429를 흉내 내 R5의 물러서기를 확인한다.

## 5. 미결정

- **기억 호출 동시 수.** 하나로 시작한다. 쌓인 일이 많을 때 둘로 늘릴지 실사용으로 본다.
- **구독 동시 사용 한도.** 구독에서 호출 두 개가 동시에 돌 때 서버 쪽에서 느려지는지는 공개된 수치가 없다. 실제로 재 본다.
