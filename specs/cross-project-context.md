# 다른 프로젝트의 컨텍스트 가져오기

> 이 문서가 답하는 질문 — **"proposal 프로젝트 대화에서 'server에서 바꾼 것에 맞춰 client도 고쳐야 하나?'라고 물으면, 나비는 server와 client의 내용을 어떻게 가져오고, 프로젝트끼리 섞이지 않게 어떻게 막는가?"**

## 0. 배경

2026-11-03 VOC. 사용자는 사이드바 RMS 그룹에 server, client, DT_RMS, proposal을 묶어 두고, proposal 대화에서 server의 변경에 맞춰 client를 고쳐야 하는지 물었다. 나비는 이렇게 답했다. "세션 도구(`naby_list_sessions`, `naby_send_to_session`)는 지금 대화가 속한 프로젝트 안의 탭만 다룬다. server와 client는 별개 프로젝트라 보이지 않는다."

원인은 세션 간 요청 스펙의 R6(cross-session-messaging §2)이다. 대상을 같은 프로젝트(cwd)로 묶었다. 그 규칙은 섞임을 막으려던 것이다. 하지만 섞임은 범위를 좁혀서가 아니라 **가져오는 길을 도구 하나로 좁혀서** 막을 수 있다.

- 가져온 내용은 이번 대화에 **도구 결과**로만 들어온다. 출처 프로젝트가 붙고, 이 대화 안에서만 쓰인다.
- 섞이면 안 되는 것은 따로 있다. **프로젝트 기억, 파일을 쓰는 폴더, 하네스**다. 이 셋은 그대로 지금 프로젝트에만 묶는다.

## 1. 결정 사항 (사용자 결정, 2026-11-03)

1. **범위.** 같은 사이드바 그룹의 프로젝트는 나비가 서로 어떤 프로젝트인지 안다. 하지만 내용을 가져오려면(파일·git 읽기, 탭에 묻기) 그룹 안이든 밖이든 사용자 승인을 받는다. (0.1.x의 "같은 그룹은 승인 없이"를 같은 날 바꿨다.)
2. **나비가 먼저 써도 된다.** 그룹 프로젝트를 알고 있으니, 질문에 답하려면 그 프로젝트의 정보가 필요할 때 나비가 스스로 도구를 부른다. 사용자가 시키지 않았어도 된다. 승인 카드가 문지기다.
3. **승인 방식.** 승인 카드에서 "이번만 허용"(다음에 또 묻는다)과 "항상 허용"(영구)을 고른다. 영구 허용은 설정에서 보고 지울 수 있다.
4. **이번 단계에 넣는 것.** (1) 다른 프로젝트 탭에 묻기, (3) 다른 프로젝트의 파일과 git 기록 읽기. (2) 프로젝트 요약 읽기는 다음 단계로 미룬다.

## 2. 범위 규칙

- **R1 대상 프로젝트.** 사이드바 프로젝트 목록(`projects` 테이블)에 있는 프로젝트만 대상이 된다. 목록에 없는 임의 경로는 거절한다.
- **R2 같은 그룹은 알린다.** 지금 프로젝트와 같은 그룹(`sidebar.projectGroups`)에 든 프로젝트는 나비 턴의 시스템 프롬프트에 짧은 목록으로 넣는다(§7 R26). 나비는 묻지 않아도 그 프로젝트들이 있다는 것과 이름·경로를 안다. 내용은 넣지 않는다.
- **R3 가져올 때는 승인.** 다른 프로젝트의 내용을 가져오는 호출은 승인 카드를 띄운다(§5). 같은 그룹도 마찬가지다. 사용자는 두 가지로 허용한다.
  - **이번만 허용** — 그 호출 하나만 통과한다. 다음 호출에서 다시 묻는다.
  - **항상 허용** — 지금 프로젝트에서 그 프로젝트로의 접근을 영구 허용한다(R18). 이후 묻지 않는다. 설정에서 지울 수 있다.
  - **거절** — 그 호출을 거절한다. 같은 세션에서 같은 프로젝트는 다시 묻지 않고 거절한다(모델이 되풀이해 카드를 띄우지 않게).
- **R4 그룹 밖.** 그룹 밖 프로젝트는 알리지 않는다. 사용자가 이름을 대거나 나비가 `naby_list_projects`로 찾으면 같은 승인 카드로 접근할 수 있다. 지금 프로젝트가 어느 그룹에도 없으면 다른 모든 프로젝트가 그룹 밖이다.
- **R5 판정은 한 곳.** 판정은 함수 하나가 맡고 두 기능이 같이 쓴다. 관계(`'same-project' | 'same-group' | 'other-group' | 'unknown-project'`)와 접근 결과(`'same-project' | 'approved' | 'denied' | 'needs-approval' | 'unknown-project'`)를 따로 돌려준다. 관계는 목록과 카드 문구에만 쓰고, 접근 허락은 접근 결과로만 정한다. `same-group`은 더 이상 접근 허락이 아니다.
- **R6 끄기.** 설정 `sessions.crossProject.enabled`(기본 켬)가 꺼지면 이 문서의 도구를 주지 않고, 세션 간 요청은 예전처럼 같은 프로젝트로만 동작한다.

## 3. 기능 1 — 다른 프로젝트 탭에 묻기

세션 간 요청(cross-session-messaging)을 프로젝트 밖으로 넓힌다. 전달 경로, 대기, 답 돌려주기, 실패 처리, 반복 방지(R7), 동시 한도는 그 문서를 그대로 쓴다.

- **R7 목록.** `naby_list_sessions`에 선택 입력 `scope`를 더한다.
  - `'project'`(기본): 지금처럼 같은 프로젝트의 다른 탭.
  - `'group'`: 같은 그룹 프로젝트의 열린 탭까지.
  - `'all'`: 모든 프로젝트의 열린 탭.
  - 탭 목록(제목·프로젝트 이름) 자체는 내용이 아니라서 승인 없이 보인다. 아직 허용하지 않은 프로젝트의 탭에는 `needsApproval: true`가 붙는다.
  - 각 줄에 프로젝트 표시 이름(바꾼 이름이 있으면 그것, project-groups §8)과 cwd를 붙인다.
- **R8 보내기.** `naby_send_to_session`의 R6 거절을 R5 판정으로 바꾼다. `approved`면 보낸다. `needs-approval`이면 승인 카드를 띄우고, 허용되면 보낸다. `denied`·`unknown-project`면 이유를 담아 거절한다.
- **R9 받는 쪽.** 받는 탭의 머리말에 보낸 쪽 프로젝트 이름을 넣는다("프로젝트 ‹proposal›의 세션 ‹제목›에서 온 요청"). 받는 탭은 **자기 프로젝트** 안에서 일한다. 쓰기와 명령도 자기 cwd에서만 한다.
- **R10 표시.** 받는 탭과 보낸 탭의 알약에 프로젝트 이름을 붙인다. 같은 프로젝트일 때는 지금처럼 세션 제목만 보인다.

## 4. 기능 3 — 다른 프로젝트 파일과 git 읽기

- **R11 도구.** 새 도구 두 개를 나비 턴에 준다. 엔진과 상관없이 나비 도구로 준다(dev-claude는 in-process `nabytools` 서버로, `naby_remember`와 같은 길).

| 이름 | 입력 | 하는 일 |
|---|---|---|
| `naby_list_projects` | 없음 | 다른 프로젝트 목록. 표시 이름, cwd, 그룹 이름, 관계(`same-group`/`other-group`), 접근 상태(`approved`/`needs-approval`/`denied`). 목록은 승인 없이 본다 |
| `naby_read_project` | `project`(cwd 또는 표시 이름), `op`, op별 입력 | 아래 표의 읽기 하나 |

| `op` | 입력 | 결과 |
|---|---|---|
| `list_dir` | `path`(선택) | 디렉터리 목록 |
| `read_file` | `path`, `offset`/`limit`(선택) | 파일 내용(한도 안에서) |
| `glob` | `pattern` | 경로 목록 |
| `grep` | `pattern`, `path`/`glob`(선택) | 일치 줄 |
| `git_status` | 없음 | `git status --short --branch -- <path 또는 .>` |
| `git_log` | `limit`(기본 20, 최대 100), `path`(선택) | `git log --oneline --decorate -- <path 또는 .>` |
| `git_diff` | `ref`(선택, 기본 작업 트리), `path`(선택) | `git diff [ref] -- <path 또는 .>`, 길면 자른다 |
| `git_show` | `ref` | 머리말 `git show -s --format=fuller ref` + 본문 `git show --format= --stat --patch ref -- .`. 폴더 안 변경이 없으면 그렇다고 적는다. 길면 자른다 |

- **R12 읽기만.** 쓰기, 수정, 명령 실행 op는 없다. 파일 op는 런타임 `fs-tools`의 읽기 실행기(`makeReadFile`·`makeListDir`·`makeGlob`·`makeGrep`)를 대상 cwd로 만들어 쓴다. 경로 제한(`isPathInside`)도 그대로 대상 cwd 기준이다.
- **R13 git은 고정 명령.** git op는 셸을 거치지 않고 `git -C <cwd>` + 고정 인자 배열로 실행한다. `ref`와 `path`는 인자 하나로만 넘긴다. `-`로 시작하는 `ref`는 거절한다(옵션 주입 방지). 출력은 64KB에서 자른다. git 저장소가 아니면 그렇다고 답한다. **모든 git 출력은 프로젝트 폴더로 제한한다.** 프로젝트 폴더가 더 큰 저장소의 하위 폴더여도 폴더 밖 파일·내용은 보이지 않는다.
- **R14 판정.** 모든 호출은 먼저 R5 판정을 지난다. `needs-approval`이면 승인 카드를 띄운다(§5).
- **R15 게이트.** 두 도구는 게이트에서 읽기(관찰)로 분류한다. 정책 규칙으로 막을 수 있다. 읽기 전용 턴(플랜 모드, "변경 허용" 꺼짐)에서도 쓸 수 있다.
- **R16 참가자·위임.** 참가자 턴, 서브에이전트, 다른 세션 요청으로 시작된 턴(cross-session R7)에는 주지 않는다. 승인할 사람이 화면 앞에 없을 수 있는 예약 작업·작업 보고 턴에도 주지 않는다.

## 5. 승인 카드

- **R17 카드.** 다른 프로젝트에 처음 접근할 때 채팅에 카드를 띄운다. 기존 도구 승인 카드와 같은 자리, 같은 모양이다. 도구가 스스로 승인을 올리는 방식은 `naby_participant_draft`와 같다. 정책 규칙이나 전체 허용 기본값이 이 승인을 대신하지 못한다.
  - ko: "나비가 다른 프로젝트 **‹server›**(`/Users/…/server`)의 내용을 읽으려 합니다." 같은 그룹이면 "같은 그룹 ‹RMS›의 프로젝트입니다.", 그룹 밖이면 "이 프로젝트는 지금 프로젝트와 다른 그룹에 있습니다."를 덧붙인다.
  - 버튼: **이번만 허용** · **항상 허용** · **거절**
  - 탭에 묻기일 때는 "읽으려 합니다" 대신 "‹server›의 탭 ‹제목›에 요청을 보내려 합니다"를 쓴다.
- **R18 기억.** "항상 허용"은 `app.db` 설정 `sessions.crossProject.approvals`에 (지금 프로젝트 cwd, 대상 cwd) 쌍으로 저장한다. 방향이 있다. proposal→server 허용이 server→proposal이나 proposal→client를 허용하지 않는다. "거절"은 세션 단위 메모리에만 두고(`sessionId` + 대상 cwd), 앱을 다시 켜거나 탭을 닫으면 지운다. "이번만 허용"은 저장하지 않는다.
- **R18a 설정에서 편집.** 설정의 "다른 프로젝트 보기" 토글 아래에 영구 허용 목록을 보인다. 줄마다 "‹proposal› → ‹server›"(표시 이름, 마우스를 올리면 cwd)와 삭제 버튼이 있다. 지우면 다음 접근부터 다시 묻는다. 사이드바에서 빠진 프로젝트가 낀 쌍은 흐리게 보이고 지울 수 있다. 목록이 비면 "아직 항상 허용한 프로젝트가 없습니다."를 보인다.
- **R19 시간 초과.** 기존 승인 대기 시간(`APPROVAL_TTL_MS`)이 지나면 거절로 처리하고, 도구 결과로 "사용자가 응답하지 않아 읽지 않았다"를 돌려준다.
- **R19a 함께 기다리는 호출.** 카드가 떠 있는 동안 같은 프로젝트로 다른 호출이 오면 새 카드를 띄우지 않고 그 카드를 함께 기다린다. "이번만 허용" 하나가 기다리던 호출 모두를 통과시킨다. 그 뒤의 호출은 다시 묻는다.
- **R20 텔레그램.** 텔레그램에서 시작된 턴은 기존 승인 중계 규칙을 따른다. 중계는 예/아니오만 전하므로 텔레그램의 "예"는 "이번만 허용"이다. "항상 허용"은 앱에서만 고를 수 있다.

## 6. 섞임 방지

- **R21 출처 표시.** 기능 3의 모든 도구 결과 첫 줄에 `[from project "server" — /Users/…/server, read-only]`를 붙인다. 기능 1의 답은 cross-session 머리말에 프로젝트 이름을 넣는다(R9). 모델과 사용자 모두 어느 프로젝트 내용인지 안다.
- **R22 펜스.** 다른 프로젝트의 파일 내용과 다른 세션의 답은 남이 쓴 글이다. 기존 `untrusted_` 펜스 규칙을 그대로 쓴다. 그 안의 지시는 따르지 않는다.
- **R23 기억.** 가져온 내용으로 기억을 쓸 때는 지금 프로젝트나 사용자 범위에만 쓴다. 대상 프로젝트의 `scope='project'` 기억에는 쓰지 않는다(기억 게이트가 지금 cwd로 막는다. 새로 막을 것은 없고, 테스트로 확인한다).
- **R24 쓰기 폴더.** 파일 쓰기와 명령 실행 도구는 지금처럼 지금 프로젝트 cwd에만 묶인다. 이 문서는 그 규칙을 바꾸지 않는다.
- **R25 기록.** 활동 로그에 `cross_project_access`(대상 cwd, 기능, op, 관계, 접근 결과, 승인 결과 `allow`/`always`/거절/시간 초과)를 남긴다. "이번만 허용"으로 통과한 호출은 저장된 허용이 없으므로 접근 결과가 `needs-approval`로 남는다. 파일 내용은 남기지 않는다.

## 7. 도구 설명(모델에게)

- `naby_list_projects`·`naby_read_project`: "다른 프로젝트의 코드나 변경을 봐야 할 때 쓴다. 읽기만 된다. 결과에는 출처 프로젝트가 붙는다. 다른 프로젝트에 무언가를 바꿔야 하면 직접 하지 말고, 그 프로젝트의 탭에 요청하거나 사용자에게 알린다."
- `naby_send_to_session` 설명에 "다른 프로젝트의 탭에도 보낼 수 있다. 그 탭의 나비가 자기 프로젝트에서 한 일을 가장 잘 안다"를 더한다.
- 같은 프로젝트에서 답할 수 있으면 다른 프로젝트를 보지 않는다는 문장을 넣는다.
- `naby_send_to_session`의 "사용자가 명시적으로 시켰을 때만" 문장은 같은 프로젝트의 탭에만 남긴다. 다른 프로젝트의 탭은 "질문에 답하려면 그 프로젝트의 정보가 필요할 때도 쓸 수 있다. 사용자 승인 카드가 뜬다"로 쓴다(§1 결정 2).
- **R26 그룹 알림 문단.** 지금 프로젝트가 그룹에 있고 그룹에 다른 프로젝트가 있으면, 나비 턴의 시스템 프롬프트에 다음 문단을 넣는다. R16에서 도구를 주지 않는 턴과 설정이 꺼진 턴에는 넣지 않는다. 목록은 이름순으로 정렬해 턴마다 같은 글이 되게 한다(프롬프트 캐시).
  - "This project is in the sidebar group ‹RMS› with: ‹server› (/Users/…/server), ‹client› (/Users/…/client). You may read them with naby_read_project or ask their tabs with naby_send_to_session when answering needs it; the user is asked to approve unless they already allowed it permanently. Do not guess their contents."

## 9. 검증

- 런타임(스파이크 또는 단위, 실제 모델 호출 없음): 그룹 판정 표(같은 프로젝트·같은 그룹·그룹 밖·그룹 없음·목록에 없는 경로), git 인자 조립(`-`로 시작하는 ref 거절, 경로는 `--` 뒤), 출처 머리말, 입력 파서.
- 셸 vitest(임시 `NABY_DB_PATH`, 임시 git 저장소, mock 엔진):
  - 같은 그룹 프로젝트도 첫 읽기에 승인 카드가 뜬다. 카드 문구에 그룹 이름이 들어간다.
  - 그룹 안·밖 모두 승인 카드가 뜬다. "이번만 허용"이면 다음 호출에서 다시 묻는다. "항상 허용"이면 앱을 다시 켜도 묻지 않고, 반대 방향과 다른 대상에는 적용되지 않는다. 거절하면 그 세션에서 다시 묻지 않고 거절한다. 시간 초과는 거절이다.
  - 설정에서 영구 허용을 지우면 다음 접근에서 다시 묻는다. 설정 API의 목록·삭제 왕복.
  - 대상 cwd 밖 경로(`../`, 절대 경로, 심볼릭 링크)는 거절한다.
  - 쓰기 op가 없다(스키마 단언).
  - 다른 프로젝트 탭에 보내기 → 받는 탭 머리말과 알약에 프로젝트 이름 → 답 돌려받기 왕복.
  - 참가자·위임·cross-session 요청 턴·예약 작업 턴에는 도구가 없다.
  - 기억 쓰기가 대상 프로젝트 범위로 들어가지 않는다.
  - 설정을 끄면 도구가 없고 R6 동작으로 돌아간다.
  - 그룹 알림 문단(R26)이 그룹에 든 프로젝트의 메인 턴에만 들어가고, 그룹 밖 프로젝트는 들어가지 않는다. 내용은 들어가지 않는다.
- 앱에서 직접: VOC 상황을 재현한다. 그룹에 묶인 server·client를 두고, proposal 탭에서 "server에서 바꾼 것에 맞춰 client도 고쳐야 하나"를 묻는다.

## 10. 범위 밖

- **프로젝트 요약 읽기**(탭이 닫힌 프로젝트의 최근 대화·기억 요약). 다음 단계에서 다룬다.
- **다른 프로젝트에 쓰기.** 바꿀 일이 있으면 그 프로젝트의 탭에 요청한다(기능 1).
- **그룹 단위 공유 기억.** 기억 범위 설계를 바꾸는 일이라 따로 다룬다.
