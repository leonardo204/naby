# 생각 중에 보낸 메시지 대기열

> 이 문서가 답하는 질문 — **"나비가 생각하는 동안 떠오른 다음 질문을 어디에 넣고, 언제 보내는가?"**
>
> 상태: 설계(2026-10-29). 사용자 의견(VOC): "나비 질문 좀 미리 넣어 두기 안 되나. 생각 중엔 입력이 안 되네." 구현은 Opus 에이전트가 한다.

## 1. 지금

작성기는 실행 중에도 글자를 칠 수 있지만(자리표시 "생성 중... 계속 입력할 수 있습니다"), Enter와 보내기 버튼이 막혀 있다(`Chat.tsx` `disabled={isLoading || liveRunning}`). 세션당 실행은 하나라서 두 번째 POST는 409가 된다. 사용자는 차례가 끝날 때까지 기다렸다가 직접 보내야 한다.

## 2. 요구사항

- **R1 대기열에 넣기.** 실행 중에 Enter(또는 보내기 버튼)를 누르면 메시지가 대기열에 들어가고 작성기는 비워진다. 첨부 이미지도 함께 들어간다. 슬래시 명령도 그대로 넣고, 보낼 때 평소처럼 해석한다.
- **R2 보이기.** 대기열은 작성기 바로 위에 "보낼 예정" 카드로 보인다. 카드마다 본문 앞부분(두 줄), 이미지 수, **수정**(작성기로 되돌리고 대기열에서 뺀다), **삭제** 버튼이 있다.
- **R3 자동 전송.** 차례가 정상으로 끝나면(실행이 idle이 되면) 대기열을 보낸다. 여러 개면 **하나로 합쳐** 한 번에 보낸다. 본문은 빈 줄로 잇고 이미지는 순서대로 모은다. 대화 기록에는 사용자 메시지 하나로 남는다. 참가자 라운드가 있는 세션에서는 라운드가 끝났을 때가 "차례가 끝났을 때"다.
- **R4 멈춤과 오류.** 사용자가 멈추거나(ESC, 중단 버튼) 차례가 오류로 끝나면 자동으로 보내지 않는다. 대기열 내용은 작성기로 되돌린다(이미 작성기에 쓰던 글이 있으면 그 뒤에 빈 줄을 두고 붙인다). 사용자가 확인하고 직접 보낸다.
- **R5 다른 탭에서 도는 세션.** 같은 세션이 다른 탭에서 실행 중일 때(`liveRunning`)도 같은 대기열을 쓴다. 실행이 끝났다는 신호(run-idle)를 받으면 보낸다.
- **R6 범위.** 대기열은 탭마다 메모리에 둔다. 앱을 끄면 사라진다. 세션을 바꾸면 그 세션 탭의 대기열로 남는다(탭이 계속 마운트되어 있으므로). 모바일 화면과 텔레그램은 이번 범위가 아니다.
- **R7 문구.** 실행 중 자리표시를 "생각하는 중입니다. 지금 보내면 끝난 뒤 이어서 보냅니다 (ESC로 중단)"로 바꾼다. 짧은 판은 "끝난 뒤 이어서 보냅니다 (ESC로 중단)". en도 같은 뜻으로 바꾼다.

## 3. 구현 위치

- 셸 클라이언트만 바꾼다. 서버·런타임 변경은 없다.
- 대기열 상태와 합치기·되돌리기는 순수 함수(`client/messageQueue.ts`)로 두고 단위 테스트한다.
- `Chat.tsx`가 대기열을 갖고, `ChatInput`은 실행 중에도 보내기를 받는다(실행 중이면 `onQueue`, 아니면 `onSend`). 자동 전송은 기존 `wrappedHandleSend`를 쓴다. 그래야 `/plan` 같은 명령이 같은 경로로 처리된다.
- 자동 전송은 한 번만 일어나야 한다. 실행 끝 신호가 두 번 와도(로컬 스트림 종료와 run-idle) 두 번 보내지 않는다.

## 4. 검증

- 순수 함수: 합치기(본문·이미지 순서), 되돌리기(작성기 글과 붙이기), 삭제·수정.
- 컴포넌트: 실행 중 Enter → 카드가 생기고 POST가 없다. 정상 종료 → POST 한 번, 합친 본문. 멈춤 → POST 없음, 작성기에 본문. 오류 → 같음. 끝 신호 두 번 → POST 한 번. 수정·삭제 버튼.

## 5. 구현 상태 (2026-10-29)

셸 클라이언트만 바꿨다. 서버와 런타임은 그대로다.

- **순수 규칙** — `client/messageQueue.ts`에 둔다. 넣기(`enqueueMessage`), 빼기(`removeQueued`·`takeQueued`), 합치기(`mergeQueued`: 본문은 빈 줄로 잇고 이미지는 순서대로 모은다), 작성기에 되돌리기(`appendToDraft`), 실행 끝 처리(`settleRunEnd`)가 여기 있다. 상태는 대기열과 "멈췄는가/오류였는가" 두 표시로 이뤄진다.
- **한 번만 보내기** — `settleRunEnd`는 처리한 뒤 언제나 빈 대기열을 돌려준다. 끝 신호가 두 번 와도 두 번째는 할 일이 없다. `Chat.tsx`는 상태를 ref에 두고 동기로 읽고 비운다. 화면용 사본은 따로 state로 둔다.
- **언제 처리하는가** — `isLoading || liveRunning`이 참에서 거짓으로 바뀔 때 한 틱 미뤄 처리한다. 보낸 탭의 스트림이 끝나면 라이브 뷰어가 이어받으면서 잠깐 "실행 중"을 보고할 수 있다. 그 틈에 실행이 다시 시작됐으면 이번 처리는 건너뛰고 다음 끝에서 처리한다. 서버는 `run-ended`를 보내기 전에 상태를 idle로 바꾸므로, 자동 전송이 409에 걸리지 않는다.
- **멈춤과 오류** — 이 채팅의 모든 중단(ESC, 대화 안 중단 버튼, 라운드 줄의 중단, 팝업에 넘기는 중단 함수)은 `handleStopRun`을 거친다. 이 함수가 "멈춤"을 표시한 뒤 원래 중단을 부른다. `onRunError`에 오류 문구가 오면 "오류"를 표시한다. 새로 보낼 때(`onRunError(null)`) 두 표시를 지운다. 둘 중 하나라도 있으면 대기열을 보내지 않고 작성기로 되돌린다.
- **작성기** — `ChatInput`은 이제 실행 중에도 막히지 않는다. `running`이면 Enter와 보내기 버튼이 `onQueue`로 간다. 되돌릴 글은 `restoreDraft`(nonce가 있는 객체)로 받아 지금 쓰던 글 뒤에 빈 줄을 두고 붙인다. 이미지도 함께 붙인다. 보이지 않는 탭에서는 포커스를 가져가지 않는다.
- **카드** — `QueuedMessages.tsx`가 작성기 바로 위(라운드 줄 아래)에 "보낼 예정" 카드를 그린다. 본문 두 줄, 이미지 수, 수정·삭제 버튼이 있다. 목록은 높이를 제한하고 그 안에서만 스크롤한다.
- **문구** — `chat.placeholderDisabled`·`placeholderDisabledCompact`를 R7대로 바꿨다(en·ko). 카드용 키 `queuedHeading`·`queuedImages`·`queuedEdit`·`queuedDelete`를 더했다.
- **검증** — 순수 함수는 `messageQueue.test.ts`, 카드 렌더와 연결은 `messageQueueWiring.test.tsx`(정적 렌더와 소스 단언)로 확인한다. 이 저장소에는 DOM 테스트 환경이 없어서, §4의 컴포넌트 검증(Enter → 카드, 종료 → POST 한 번 등)은 같은 규칙을 순수 함수 단위로 고정하고 연결은 소스 단언으로 확인하는 방식으로 대신했다.

남은 점:

- 자동 전송 자체가 실패하면(네트워크 오류 등) 그 메시지는 대기열로 돌아오지 않는다. 대화 기록에 사용자 메시지로 남으므로 다시 보내기 버튼으로 보낼 수 있다.
- 대기열이 있는 동안 메시지 다시 보내기와 ChatContext로 들어오는 메시지는 여전히 기존 규칙(실행 중이면 무시 또는 409)을 따른다. 대기열로 보내지 않는다.
- 실제 브라우저에서 확인하지 못한 것: 카드 배치와 높이, 실행이 다른 탭에서 끝날 때의 run-idle 처리, 참가자 라운드가 끝날 때의 시점.

## 6. 자동 전송 뒤 말풍선이 사라지던 문제 (0.1.2)

차례가 끝나면 두 가지가 거의 동시에 일어난다. 대기열이 다음 메시지를 바로 보내고, 끝난 턴을 디스크와 맞추는 읽기(reconcile)가 나간다. 읽기 응답이 새 턴을 시작한 뒤에 도착하면 화면의 메시지 목록을 디스크 내용으로 바꾼다. 그 바람에 방금 보낸 사용자 말풍선과 나비의 답이 사라졌다가 새 턴이 끝나야 다시 보였다(2026-10-29 실기 보고). 그 사이 답의 스트림 이벤트는 붙을 말풍선이 없어 `system/status` 같은 칩으로 보였다.

고친 방법은 이렇다. `Chat.tsx`가 턴마다 번호(`turnGenRef`)를 매긴다. 실행 중 상태로 바뀔 때와 대기열이 자동 전송할 때 번호를 올린다. 턴이 끝날 때 나가는 두 읽기(보낸 탭의 `reconcileFromDiskRef`, 지켜보는 탭의 `onComplete`)는 나갈 때의 번호를 기억한다. 응답이 왔을 때 번호가 바뀌었으면 반영하지 않는다(`loadHistoryByCwdAndSessionId`의 `shouldApply`). 버린 읽기는 새 턴이 끝날 때 하는 읽기가 대신한다.
