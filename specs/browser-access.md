# 같은 PC의 브라우저에서 나비 쓰기 (원격 접속 1단계)

## 0. 요약

나비 화면은 이미 웹 페이지다. Electron 창은 앱 안에서 도는 Next 서버(`127.0.0.1`의 무작위 포트)를 띄울 뿐이다. 이 문서는 그 서버에 **같은 PC의 브라우저가 안전하게 들어오는 문**을 하나 더 낸다. 앱 메뉴의 "브라우저에서 열기"가 한 번만 쓰는 코드를 붙여 기본 브라우저를 열고, 서버는 그 코드를 브라우저 전용 쿠키로 바꿔 준다. 기존의 네 가지 보호 장치는 그대로 둔다.

전체 로드맵은 세 단계다. 이 문서는 1단계만 확정한다.

| 단계 | 내용 | 문서 |
|---|---|---|
| 1 | 같은 PC의 브라우저 | 이 문서 |
| 2 | 폰에서 내 PC로 (사설망 Tailscale 우선, 같은 Wi-Fi 보조, QR 기기 연결) | 후속 `remote-access` (미작성) |
| 3 | 기기 사이 이어 쓰기 다듬기 (초안·열린 대화 넘기기) | 후속 |

클라우드 서버는 두지 않는다. 데이터는 지금처럼 PC의 `app.db` 하나에 있고, 브라우저는 같은 서버를 보는 화면이 하나 더 생기는 것뿐이다.

## 1. 지금

- 서버는 `electron/next-server.ts`가 `listen(0, '127.0.0.1')`로 연다. 포트는 실행할 때마다 바뀐다.
- `electron/hardening.ts`의 가드가 모든 요청에 네 가지를 검사한다. Host가 `127.0.0.1:<port>`와 정확히 같은지, Origin이 있으면 같은 출처인지(WebSocket은 Origin 필수), 바인드가 루프백인지, 실행마다 새로 만든 세션 토큰이 있는지다. 토큰은 첫 탐색에서만 쿼리로 오고, 가드가 HttpOnly·SameSite=Strict 쿠키로 바꿔 준다.
- 창은 `win.loadURL(windowUrl('/'))`로 토큰을 실은 주소를 연다. 이 토큰은 preload의 `window.naby.sessionToken`으로도 노출된다.
- 그래서 지금은 같은 PC의 브라우저도 들어오지 못한다. 토큰을 모르기 때문이다. 이것은 의도된 설계다. 루프백은 인증 경계가 아니어서, 토큰이 없으면 PC의 다른 프로세스나 사용자가 연 웹 페이지가 나비를 조종할 수 있다(CVE-2025-52882와 같은 유형).
- 한 세션을 여러 화면이 보는 구조는 이미 있다. 실시간 보기(`useLiveStream`), 세션당 실행 하나(409), 메시지 대기열(chat-message-queue)이 그것이다.
- 브라우저에 없는 기능은 preload가 `window.naby`로 노출하는 것들이다. 목록은 §2.6에 있다.

## 2. 요구사항

### 2.1 진입: "브라우저에서 열기"

- **R1** 앱 메뉴(macOS 앱 메뉴 / Windows·Linux 파일 메뉴)와 **설정 → 브라우저 지원** 섹션에 "브라우저에서 열기" 항목을 둔다(2026-10-30 사용자 결정). 이 섹션에는 "브라우저 접속 끊기"(R8)와 지금 연결된 브라우저 수도 함께 보인다. 누르면 OS 기본 브라우저로 `http://127.0.0.1:<port>/?pair=<코드>`를 연다(`shell.openExternal`).
- **R2** 주소는 항상 `127.0.0.1`을 쓴다. `localhost`는 쓰지 않는다. 가드의 Host 검사가 정확히 일치를 요구하고, 이 규칙은 DNS 리바인딩을 막는 장치라 느슨하게 만들지 않는다.

### 2.2 인증: 일회용 코드와 브라우저 쿠키

- **R3** 창의 세션 토큰을 브라우저 주소에 싣지 않는다. 주소는 브라우저 기록과 동기화된 기록에 남기 때문이다. 대신 main 프로세스가 **일회용 연결 코드**를 만든다. 코드는 무작위 32바이트, 유효 시간 60초, 한 번 쓰면 사라진다.
- **R4** 코드는 main 프로세스에서만 만든다. 서버 HTTP API로 발급하는 경로를 두지 않는다. 그래야 PC의 다른 프로세스가 코드를 얻을 수 없다(토큰을 모르면 API도 못 부르지만, 발급 경로 자체를 없애 두 번째 벽으로 삼는다).
- **R5** 가드는 `?pair=<코드>`가 붙은 첫 요청을 받으면 코드를 검사하고 소모한다. 맞으면 **브라우저 전용 토큰**을 새로 만들어 쿠키로 준다(HttpOnly, SameSite=Strict, Path=/). 이 토큰은 창 토큰과 다른 값이고, 가드는 두 토큰을 모두 받아들인다. 응답은 `?pair=`를 뺀 주소로 리다이렉트해, 쓴 코드가 주소창과 기록에 남지 않게 한다.
- **R6** 코드가 틀렸거나 만료됐거나 이미 쓰였으면 403과 함께 "나비 앱의 '브라우저에서 열기'로 다시 열어 주세요" 안내 페이지를 보인다. 이유는 지금처럼 로컬 로그에만 남긴다.
- **R7** 브라우저 토큰은 앱이 실행되는 동안만 유효하다. 앱을 다시 켜면 포트와 토큰이 모두 바뀌므로 "브라우저에서 열기"를 다시 누른다.
- **R8** 설정에 "브라우저 접속 끊기"를 둔다. 누르면 발급된 브라우저 토큰을 모두 폐기한다. 이미 열린 브라우저 탭은 다음 요청부터 403을 받고, WebSocket은 끊는다.

### 2.3 Host·Origin 검사

- **R9** 기존 검사를 그대로 쓴다. 브라우저도 `http://127.0.0.1:<port>`에서 열리므로 Host·Origin이 앱 창과 같다. 검사 규칙을 바꾸거나 예외를 늘리지 않는다.

### 2.4 같은 세션을 두 화면에서

- **R10** 앱 창과 브라우저 탭이 같은 세션을 보면 기존 규칙을 따른다. 한 세션에는 실행이 하나뿐이다. 다른 화면에서 실행 중이면 이쪽은 실시간 보기가 되고, 입력은 대기열에 들어간다.
- **R11** 열린 탭 목록(프로젝트 상태)은 서버에 있으므로 두 화면이 공유한다. 브라우저에서 탭을 닫으면 앱 창에서도 닫힌다. 이 동작은 1단계에서 그대로 둔다. 화면마다 따로 두는 것은 3단계에서 다룬다.
- **R12** 앱을 종료하면 브라우저 탭은 연결이 끊긴다. 기존 연결 상태 줄(chat-connection-status)이 그 상태를 보인다. 이 경우에도 "나비 앱이 꺼져 있습니다. 앱을 켜고 '브라우저에서 열기'로 다시 여세요"라고 안내한다.

### 2.5 기본 브라우저 보안

- **R13** 브라우저 쪽 응답에도 앱 창과 같은 보안 헤더(CSP 등)를 쓴다. 앱 창 전용으로 완화된 헤더가 있으면 목록을 만들어 브라우저에는 적용하지 않는다.
- **R14** 브라우저 쿠키는 다른 사이트에서 오는 요청에 실리지 않는다(SameSite=Strict). 다른 사이트의 페이지가 나비 API를 부르는 경로는 Origin 검사와 이 쿠키 규칙 두 겹으로 막는다.

### 2.6 브라우저에 없는 기능

화면 코드는 `window.naby`가 없을 때를 처리해야 한다. 기능별로 이렇게 한다.

| `window.naby` 기능 | 쓰는 곳 | 브라우저에서 |
|---|---|---|
| `credentials`, `providers` | AI 프로바이더 설정(키 입력) | 키 입력 칸 대신 "키는 나비 앱 창에서 설정합니다" 안내. 상태 보기만 서버 API로 가능하면 보인다 |
| `onboarding` | 첫 실행 마법사 | 브라우저에서는 띄우지 않는다 |
| `updates`, `whatsNew` | 업데이트 패널, 새 기능 안내 | 숨긴다 |
| `chatgptOauth` | ChatGPT 구독 로그인(개발용) | 숨긴다 |
| `fsOps` | 파인더에서 보기, 기본 앱으로 열기, 휴지통 | 메뉴 항목을 숨긴다 |
| `notifications` | 턴 완료 OS 알림 | §2.7 규칙으로 앱과 브라우저 중 한 곳에서만 띄운다 |
| `getPathForFile` | OS에서 끌어 놓은 파일의 절대 경로 | 경로는 얻을 수 없다. 파일 내용을 올리는 경로만 쓴다 |

- **R15** 판정 함수는 하나만 둔다(`isDesktopApp()` 같은 것). 각 화면이 `window.naby` 존재를 따로 검사하지 않는다(CLAUDE.md의 "같은 질문에 답하는 함수가 둘이면 UI가 틀린 쪽을 믿는다").
- **R16** 숨긴 기능 자리에 빈칸이 남지 않게 한다. 꼭 필요한 곳(프로바이더 설정)만 안내 문구를 둔다.

### 2.7 턴 완료 알림은 한 곳에서만 (2026-10-30 사용자 결정)

- **R18** 턴이 끝났을 때 알림은 **지금 사용자가 보고 있는 곳 하나**에서만 띄운다. 앱 창과 브라우저가 둘 다 띄우지 않는다.
  - 브라우저 탭이 활성(포커스가 있고 화면에 보이는 상태)이면 그 브라우저 탭이 브라우저 알림(Notification API)을 띄운다.
  - 앱 창이 활성이면 앱이 띄운다(지금 동작).
  - 둘 다 활성이 아니면 앱이 OS 알림을 띄운다.
- **R19** 판정은 서버가 한다. 각 화면(앱 창, 브라우저 탭)은 포커스·보임 상태가 바뀔 때마다 서버에 알린다. 기존 `/ws/global-state` 연결에 화면 종류(`app` | `browser`)와 함께 싣는다. 턴이 끝나면 서버가 가장 최근에 활성이 된 화면을 고르고, 그 화면에만 "알림을 띄워라" 신호를 보낸다. 활성 화면이 없거나, 고른 브라우저 탭의 연결이 끊겼으면 앱이 띄운다.
- **R20** 브라우저 알림 권한은 처음 브라우저로 들어왔을 때 묻지 않는다. 브라우저가 알림 대상으로 처음 뽑혔을 때, 또는 설정 → 브라우저 지원의 "브라우저 알림 켜기"를 눌렀을 때 묻는다. 권한이 없거나 거절됐으면 그 알림은 앱이 대신 띄운다.
- **R21** 알림 문구는 지금처럼 정해진 목록에서 고른다. 브라우저 쪽도 같은 문구 키를 쓴다.

### 2.8 기록

- **R17** 코드 발급, 코드 사용(성공·실패 이유), 브라우저 토큰 폐기를 활동 로그에 남긴다. 코드와 토큰 값은 남기지 않는다.

## 3. 범위 밖

- 다른 기기(폰·다른 PC)에서의 접속. 바인드는 `127.0.0.1`을 유지한다. 2단계에서 별도 문서로 다룬다.
- 포트 고정과 북마크. §4의 결정 항목이다. 정하기 전까지는 R7대로 실행마다 다시 연다.
- 기기·화면 사이 동기화(초안, 열린 탭 배치, 읽음 표시). 3단계다.
- 앱 없이 서버만 띄우는 모드(헤드리스). 지금 구조는 Electron main이 자격 증명 보관과 서버 수명을 맡는다.

## 4. 결정 (2026-10-30 사용자 결정)

1. **포트는 고정하지 않는다.** 실행마다 포트와 토큰이 바뀌고, 앱을 다시 켜면 "브라우저에서 열기"를 다시 누른다(R7). 실행 사이에 남는 토큰을 만들지 않는다.
2. **턴 완료 알림은 지금 활성인 곳 한 곳에서 띄운다.** 브라우저와 앱 중 하나다. 둘 다 활성이 아니면 앱이 띄운다(§2.7).
3. **설정 진입점은 설정 → 브라우저 지원이다**(R1).

## 5. 작업 계획

| ID | 내용 | 레이어 | 검증 |
|---|---|---|---|
| BA-1 | 일회용 코드 발급(main)과 가드의 코드 교환·브라우저 토큰·리다이렉트·폐기(R3~R9) | `electron/hardening.ts`, `next-server.ts`, `ipc.ts` | `spike-entry` 확장: 코드 1회성, 60초 만료, 틀린 코드 403, 폐기 후 403·WS 끊김, Host·Origin 규칙 불변 |
| BA-2 | "브라우저에서 열기" 메뉴와 설정 항목, "브라우저 접속 끊기"(R1, R2, R8) | `electron/menu-template.ts`, 셸 설정 | 메뉴 템플릿 테스트, 설정 렌더 테스트 |
| BA-3 | `isDesktopApp()` 하나와 Electron 전용 기능 숨김·안내(R15, R16, §2.6 표) | 셸 클라이언트 | `window.naby` 없는 렌더 테스트(기능별) |
| BA-4 | 연결 끊김 안내와 403 안내 페이지(R6, R12) | 셸 클라이언트, 가드 응답 | 렌더 테스트, 가드 응답 테스트 |
| BA-5 | 활동 로그(R17) | main, 셸 | 로그 필드 테스트(값 미포함) |
| BA-6 | 알림 대상 판정(R18~R21): 화면 활성 상태 보고, 서버 판정, 브라우저 알림과 권한 | 셸 서버(`/ws/global-state`), 클라이언트, main 알림 | 판정 순수 함수 테스트(활성 조합별), 권한 거절 시 앱 대체 테스트 |

순서는 BA-1 → BA-3 → BA-2 → BA-4 → BA-6 → BA-5다. BA-1이 보안의 핵심이라 먼저 하고 스파이크로 검증한다. BA-3을 먼저 해 두면 BA-2가 열리는 순간 브라우저 화면이 깨지지 않는다.

## 6. 검증

- 보안 회귀는 `electron/spike-entry.ts`(실제 서버를 띄워 Host·Origin·토큰을 시험하는 스파이크)로 잡는다. 기존 시험 항목은 그대로 통과해야 한다.
- 브라우저 화면은 패키징본에서 확인한다. 개발 서버는 `node:sqlite` 문제로 `/api/naby`가 500을 낸다(CLAUDE.md).
- 실기 확인 항목: 브라우저에서 프로젝트·그룹·세션 목록, 대화 보내기, 앱 창과 같은 세션 동시 보기, 앱 종료 후 끊김 안내, "브라우저 접속 끊기" 후 403, 알림이 활성 화면 한 곳에서만 뜨는지(브라우저 활성 / 앱 활성 / 둘 다 비활성).
