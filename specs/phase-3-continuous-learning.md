# Phase 3 P3-M8 — 연속 학습 (세션 회고와 암묵 라벨)

> 상태: 설계 확정(2026-07-30). **M8a·M8b·M8c 구현 완료**(§4.8, §5.6, §6.6). 다음은 M8d다.
> 한 줄 요약: 대화가 쌓여도 배우지 않는 구조를 고친다. 세션이 끝나면 대화록을 되돌아보고, 거기서 나온 증거가 원장과 기억으로 흘러들게 한다.

## 1. 문제 — 대화가 쌓여도 배우지 않는다

지금 구조에서 세션이 100개 쌓여도, 대화가 아무리 길어져도, 에이전트는 거의 배우지 않는다. 공백은 다섯 개다.

1. **대화록이 통째로 미사용이다.** `messages` 테이블에 전체 트랜스크립트가 저장되지만(`src/runtime/session.ts`), 성장 지표도 기억 시스템도 이를 읽지 않는다.
2. **`correctedAfter`에 쓰는 코드가 없다.** 원장 계약(§2)이 "묻지 않고 처리한 뒤 사용자가 사후에 고쳤는가"를 자율 행동의 오류 신호로 예약했지만 writer가 없다. 그래서 recall은 항상 1이고 coverage는 부풀기만 한다.
3. **세션 종료 이벤트가 없다.** `sessions.status='ended'`는 어디서도 기록되지 않아 "끝났으니 되돌아보자"를 걸 자리가 없다.
4. **기억이 단발이다.** 추출·병합·모순 해소·감쇠·관련도 랭킹이 없고, `proposed`는 사람이 승인하기 전에는 영원히 잠들어 있다.
5. **라벨 공급원이 하나다.** 지표 전체가 모델이 자발적으로 부르는 `naby_checkin`에 의존한다. 안 부르면 지표가 얼어붙는다.

## 2. 원칙 — 개수를 세지 않는다는 결정은 유지한다

butterfly-trust-meter §2의 결정(대화 수·기억 수 누적은 신뢰 신호가 아니다)은 그대로 둔다. 세션 수를 지표에 직접 넣으면 틀린 사실 50개를 저장한 에이전트가 만개한 것으로 표시되는 문제로 되돌아간다.

대신 인과 사슬을 배선한다. **대화량 → 증거량 → 성장.** 세션이 많고 길수록 암묵 라벨과 학습 재료가 많이 생산되게 하면, 개수를 세지 않아도 Wilson 하한이 자연스럽게 더 빨리 조여진다. 성장이 대화량의 함수가 되는 것이 아니라, 대화량이 증거를 낳고 증거가 성장을 낳는다.

## 3. 구조 — 네 축과 마일스톤

| 축 | 내용 | 마일스톤 |
|---|---|---|
| A. 세션 회고 | 놀고 있는 세션의 대화록을 읽어 암묵 교정을 원장에 기록한다 | **M8a** |
| B. 기억 통합 | 회고가 기억 후보를 제안하고, 병합·모순 해소·교차 세션 확증을 돌린다 | M8b |
| C. 관련도 주입 | 주입 랭킹을 scope→type→최신순에서 관련도 기반으로 바꾸고 학습 깊이를 표시한다 | M8c |
| D. 원장 편입 | 검증된 암묵 라벨을 가중해 원장에 편입하고 골든셋 재채점을 돌린다 | M8d |

나비 게이트는 계속 명시 체크인 중심이다. 암묵 라벨은 커버리지·recall 축부터 채우고(M8a), 정확도 축 편입은 M8d에서 가중치를 정한 뒤에 한다.

## 4. M8a — 세션 회고 1차 (암묵 교정)

### 4.1 범위

죽어 있는 축 하나를 살리는 것만 한다. 자율 행동(`autonomous` 이벤트) 뒤에 사용자가 결과를 고쳤는지를 대화록에서 찾아 `correctedAfter=true`를 기록한다. 기억 제안(M8b), 원장 정확도 편입(M8d)은 하지 않는다.

### 4.2 세션 종료는 판정하지 않고 휴지로 정의한다

데스크톱 앱에서 사용자는 세션을 닫지 않고 떠난다. "종료됨"을 기록하려는 시도는 writer가 애매해서 §1-3과 같은 공백을 다시 만든다. 그래서 회고 대상은 상태가 아니라 휴지로 정한다.

> 회고 대상 = `last_used_at`이 `REFLECTION_IDLE_MS`(기본 30분) 이전이고, 마지막 회고 커서 이후 새 메시지가 있는 세션.

`sessions.status`는 건드리지 않는다.

### 4.3 트리거 — 타이머가 아니라 다음 대화가 돈다

상시 타이머를 두지 않는다. 엔진 run이 시작될 때, 지금 쓰는 세션을 제외한 휴지 세션들을 fire-and-forget으로 회고한다. 앱을 쓰는 동안에만 돌고, 턴을 늦추지 않으며, 백그라운드 데몬이 없다. 한 번의 스윕은 최대 `REFLECTION_SWEEP_CAP`(기본 3) 세션까지만 처리한다. 테스트와 수동 실행을 위해 `POST /api/naby {action:'reflection.run'}`을 둔다.

### 4.4 판정자(judge)는 모델이되, 검증은 결정론이다

암묵 교정 탐지는 언어 이해가 필요해서 저비용 모델 호출로 한다. 단, 모델 출력은 그대로 믿지 않는다.

- **입력은 사건 단위다.** 순수 함수가 각 `autonomous` 이벤트와 그 뒤에 이어진 사용자 메시지 창을 짝지어 사건 목록을 만든다. 이미 `correctedAfter`가 붙은 이벤트, `checkin`·`tripwire` 이벤트는 입력에서 뺀다.
- **출력은 구조화 판정이다.** 사건 id별로 `corrected` 여부와 `evidenceQuote`(근거가 된 사용자 발화 인용)를 낸다.
- **검증기가 지어낸 판정을 버린다.** `evidenceQuote`가 해당 사건 이후의 실제 사용자 메시지에 부분 문자열로 존재하지 않으면 그 판정은 기각한다. 입력에 없던 사건 id를 가리키는 판정도 기각한다. 모델이 환각으로 교정을 만들어낼 수 없다.
- **판정자는 주입 seam이다.** 스파이크는 mock judge를 꽂아 실제 스윕·검증기·스토어를 구동한다. spike:learn과 같은 기법이다.

원장 불변식 5(에이전트는 원장을 읽을 수 없다)와의 관계: 회고는 턴 밖에서 도는 별도 평가자이고, 결과는 원장에만 쓴다. 채점당하는 에이전트의 턴 안으로는 아무것도 돌아가지 않는다.

### 4.5 계약 변경 (checkin-contracts 0.4.0으로 반영)

- 스토어 메서드 추가: `markEvalEventCorrected(id): boolean`. `kind='autonomous'`인 행에만 동작하고, payload의 `correctedAfter`만 바꾼다. 원장에서 사후 변경이 허용되는 유일한 필드다.
- `listEvalEvents`에 `sessionId` 선택자를 추가한다. 회고가 세션 단위로 자율 이벤트를 읽어야 한다.
- 회고 커서 저장: 새 테이블 `reflection_state(session_id PK, last_seq, reflected_at)`. 스키마 버전 7→8. 세션 삭제 시 함께 지운다(원장과 달리 커서는 사용자 기록이 아니라 진행 상태다).

### 4.6 구현 배치

| 위치 | 내용 |
|---|---|
| `src/runtime/reflection.ts` (순수) | 휴지 판정, 사건 목록 구성, 판정 검증기, 상수. 프로바이더와 IO가 없다 |
| `src/runtime/store/*` | `markEvalEventCorrected`, `listEvalEvents` sessionId 선택자, `reflection_state` 커서, 마이그레이션 v8. 두 드라이버 모두 |
| 셸 `lib/reflection.ts` | 스윕 오케스트레이션(due 세션 찾기 → 메시지·이벤트 로드 → judge 호출 → 검증 → 기록 → 커서 전진), 프로덕션 judge(기존 모델 호출 경로 재사용 — 새 프로바이더 해석 사본을 만들지 않는다) |
| 셸 `engines/naby.ts` | run 시작 시 fire-and-forget 스윕 |
| 셸 `api/naby.ts` | `reflection.run` 액션 |

UI 작업은 없다. GrowthPanel이 이미 `correctedAfter`를 표시하고 있고, 지금까지 항상 0이었을 뿐이다.

### 4.7 검증 계획

- 신규 스파이크 `npm run spike:reflection` — mock judge로 확인한다: 휴지 판정, 커서 전진과 멱등성(두 번째 스윕은 no-op), 인용 검증기가 지어낸 판정을 기각, `autonomous` 외 이벤트는 못 건드림, 기록된 `correctedAfter`가 `computeGrowth`의 missedAsks·recall·coverage에 실제로 반영됨.
- 셸 vitest — 스윕 오케스트레이션과 `reflection.run` 액션.
- 회귀 — `spike:growth`, `spike:checkin`, `spike:02`, `spike:autonomy`, 셸 전체 테스트, 타입체크(양 트리), `build:app`.
- 미검증으로 남는 것 — 라이브 모델 judge의 판정 품질. mock으로는 배선만 증명된다.

### 4.8 구현 상태 — ✅ 완료(2026-07-30)

`npm run spike:reflection` **18/18 PASS**(두 드라이버), 회귀 spike 4종 전부 PASS, 셸 테스트 453/453, 타입체크 clean(양 트리, 기존 베이스라인 4건 제외), `build:app` exit 0. 구현하며 확정된 설계가 넷 있다.

- **사건↔메시지 결합은 시간이 아니라 구조로 한다.** `messages`에는 타임스탬프가 없어 이벤트의 `at`과 비교할 수 없다. 대신 게이트가 결과적 호출마다 정확히 한 행을 쓰고 `runTurn`이 호출마다 tool 메시지 하나를 쓰는 대응을 이용해, 같은 도구 이름의 n번째 이벤트를 n번째 tool 메시지에 앵커한다. 앵커를 못 찾는 이벤트는 추측하지 않고 사건에서 뺀다.
- **judge는 ai-sdk(API 키) 경로만 쓴다.** `resolveProviderCredential` + `makeModelResolver`를 재사용하되 `runTurn`을 거치지 않아 사용자 세션에 트랜스크립트·usage 행을 남기지 않는다. 로컬 Claude 로그인만 있는 기기에서는 자격 해석이 실패하고 회고는 로그 한 줄과 함께 건너뛴다 — 엔진 선택 분기를 복제하지 않는다.
- **멱등 장치가 두 겹이다.** `markEvalEventCorrected`는 이미 표시된 행에 재호출해도 쓰기 없이 true를 돌려주고, 스윕은 프로세스당 single-flight라 연속 턴이 커서 경쟁을 만들지 않는다. judge 실패 시 커서는 전진하지 않아 다음 스윕이 재시도한다.
- **사건은 커서 이후의 사용자 메시지가 있을 때만 성립한다.** 휴지 판정과 별개의 안전벨트로, 이미 판정한 구간이 모델 호출을 두 번 쓰지 못하게 한다.

## 5. M8b — 세션 회고 2차 (기억 제안과 통합)

### 5.1 범위

회고 judge가 교정 탐지에 더해 기억 후보를 추출하고, 결정론적 통합이 교차 세션 확증을 추적한다. 의미 기반 근사 중복 병합(다른 key, 같은 뜻)은 하지 않는다 — 임베딩 없이는 추측이 되므로 미결정으로 남긴다(§8).

### 5.2 회고의 기억 제안

- **judge 호출은 세션당 1회 그대로다.** 같은 호출이 두 과업을 낸다: `{corrections: [...], memories: [...]}`. 기억 후보는 `{scope, type, key, value, evidenceQuote}`.
- **검증기가 M8a와 같은 원칙으로 지어낸 제안을 버린다.** `evidenceQuote`가 그 세션의 실제 사용자 메시지에 부분 문자열로 존재해야 한다.
- **쓰기는 `naby_remember`와 같은 게이트를 지난다.** `proposed` + `artifact` 등급 고정, `looksLikeSecret` 거부, `normalizeMemoryKey`, 값 400자 상한, `org` 스코프 금지, cwd 없는 세션의 `project` 금지. 회고라고 해서 게이트가 느슨해지지 않는다.
- **`provenance.createdFrom = "<sessionId>:<seq>"`** — 근거가 된 사용자 메시지의 좌표. 기억 계약 §3이 예약한 "message id" 연결의 실체화다.

### 5.3 확증(corroboration) 추적

- 새 테이블 `memory_observations(memory_id, session_id, observed_at, created_from, PK(memory_id, session_id))`. 스키마 버전 8→9.
- **관측 기록은 스토어가 자동으로 한다.** `putMemory`가 `provenance.sessionId`를 담은 요청을 안착시키면 관측 행을 함께 남긴다. 회고 경유와 `naby_remember` 경유가 자연히 같은 확증 풀에 쌓이고, 별도 호출을 잊을 수 없다.
- **값이 실질적으로 바뀌면 관측을 비운다.** 새 주장에는 새 증거가 필요하다. 그래서 확증 수 = **현재 값에 동의한 서로 다른 세션 수**이고, "모순 없음" 조건이 따로 필요 없다.
- 관측은 커서처럼 진행 상태가 아니라 증거지만, 근거 대화가 지워지면 함께 지운다 — 세션 삭제가 그 세션의 관측 행을 지우고, 기억 삭제가 그 기억의 관측을 지운다. 이미 confirmed된 항목이 관측 감소로 되돌아가지는 않는다.

### 5.4 승인 큐와 옵트인 자동 confirm

- 기억 검토 API가 항목별 확증 수를 함께 내고, 검토 UI는 `proposed`를 확증 수 내림차순으로 정렬하며 "세션 N회 관측" 배지를 단다. 사람이 가장 검증된 후보부터 본다.
- 설정 `memory.autoConfirmCorroborated`(기본 꺼짐). 켜면 통합 단계가 **artifact 등급이고 확증 ≥ `CORROBORATION_THRESHOLD`(3)인** `proposed`를 `confirmed`로 승격하고 로그를 남긴다. `external`은 설정과 무관하게 절대 자동 confirm되지 않는다 — 기억 계약 §4 불변식 1은 그대로다.
- 통합 단계는 회고 스윕 끝에 돈다. 별도 타이머를 만들지 않는다(§4.3과 같은 이유).

### 5.5 검증 계획

- 스파이크(회고 스파이크 확장 또는 신규) — 제안이 `proposed`+`artifact`+`createdFrom`으로 안착, 환각 인용 기각, 시크릿 기각, 세션 3회 확증 집계, 값 변경 시 확증 리셋, 옵트인 꺼짐이면 승격 없음/켜짐이면 승격, external 미승격, `proposed` 미주입 불변 유지, v8→v9 마이그레이션.
- 셸 — 확증 수 노출·정렬, 토글 배선, 검토 UI 배지.
- 회귀 — M8a와 같은 전체 세트.

### 5.6 구현 상태 — ✅ 완료(2026-07-30)

`npm run spike:reflection` **34/34 PASS**(두 드라이버), 회귀 spike 7종 전부 PASS, 셸 테스트 472/472, 타입체크 clean(양 트리, 기존 베이스라인 4건 제외), `build:app` exit 0. 구현하며 확정된 설계가 다섯 있다.

- **judge 응답은 두 모양을 받는다.** 계약상 답은 `{corrections, memories}` 객체이지만, 맨 배열도 "교정만, 제안 없음"으로 읽는다. M8a judge의 응답 모양이 그것이고, 두 과업 지시를 받은 모델도 종종 그 모양으로 답한다. 파서는 **바깥 괄호가 먼저 나온 쪽**으로 판별한다 — 객체를 먼저 찾으면 배열의 첫 원소를 답 전체로 오독해 조용히 침묵이 된다.
- **세션 컨텍스트는 judge의 두 번째 인자다.** `judge(cases, context)`로 넓혀서 M8a의 mock judge가 한 줄도 바뀌지 않는다. 컨텍스트가 없으면 프롬프트는 M8a와 글자 그대로 같은 교정 전용 호출이 된다.
- **사건이 없는 세션은 여전히 judge를 부르지 않는다.** §4.3의 트리거 규칙을 기억 제안이 넓히지 않는다. 넓혔다면 자율 행동이 없는 모든 휴지 세션마다 모델 호출이 하나씩 붙었을 것이다.
- **확증 임계값은 서버가 UI로 내려준다.** 검토 패널은 런타임을 **타입으로만** 임포트한다(값을 넘기면 node 코드가 브라우저 번들에 들어간다). 한국어 문장 안에 3을 손으로 적어두면 §7이 값을 조정하는 날 조용히 틀린다.
- **자동 승인 판정은 스토어 밖 순수 함수다.** `shouldAutoConfirmMemory`가 네 조건(external 절대 불가 · 설정 켜짐 · 아직 proposed · 임계값 충족)을 한자리에 적는다. 쓰기 경로 안에 숨은 정책은 아무도 찾지 못하는 정책이다.

미검증으로 남는 것 — 라이브 모델이 뽑는 기억 후보의 품질, 그리고 `CORROBORATION_THRESHOLD` 3의 적정성(§8). mock으로는 배선과 게이트만 증명된다.

## 6. M8c — 관련도 주입과 학습 깊이

### 6.1 범위 — 임베딩 없이 시작한다

관련도 랭킹의 1차는 **결정론적 어휘(lexical) 점수**다. 임베딩은 프로바이더 호출·벡터 저장·드리프트 관리를 끌고 들어오는데, 지금 병목은 그게 아니다 — 2000토큰 예산 안에 "이번 턴과 무관한 기억"이 최신순이라는 이유로 먼저 들어가는 것이다. 토큰 겹침만으로도 그 병목은 풀리고, 결과가 재현되고, 스파이크로 검증된다. 임베딩(그리고 그에 기대는 의미 기반 근사 중복 병합)은 어휘 랭킹의 한계가 실측되면 올린다(§8).

### 6.2 관련도 랭킹

- **주입 질의에 턴 텍스트가 실린다.** `MemoryInjectionQuery`에 `queryText?: string`(이번 턴의 사용자 입력)을 추가한다 — 기억 계약 §5의 가산적 개정(0.4.0).
- **점수는 토큰 겹침이다.** 소문자화, 비문자·숫자 경계 분리(한글 시퀀스 유지), 1글자 토큰 제거 후 기억(key+value)과 질의의 겹침을 정규화해 점수로 쓴다. 순수 함수이고 모델 호출이 없다.
- **동점은 기존 순서가 가른다.** 관련도가 같으면 기존 scope→type→최신순 비교자로 떨어진다. 계약 §5의 "동점 시 스코프 우선" 불변식이 그대로 지켜진다.
- **신호가 없으면 기존 동작 그대로다.** `queryText`가 없거나 어떤 후보도 겹침이 없으면 랭킹은 기존 정렬과 동일하다 — 관련도가 도움이 안 되는 턴을 지금보다 나쁘게 만들지 않는다.
- 예산 로직(하드 캡, `droppedForBudget` 집계)은 건드리지 않는다.

### 6.3 학습 깊이 축 — 신뢰와 다른 말을 한다고 명시한다

`growth.get` 응답에 `learning` 블록을 추가하고 성장 패널이 별도 섹션으로 렌더한다.

- 담는 것: 스코프별 확정 기억 수, 검토 대기(`proposed`) 수, 확증 2회 이상 항목 수, 원장의 서로 다른 작업 유형 수, 마지막 회고 시각.
- **나비 게이트에 넣지 않는다.** butterfly-trust-meter §2의 결정(개수는 신뢰가 아니다)이 이 축을 게이트 밖에 두는 이유다. 패널 문구가 이를 직접 말한다 — "이 숫자는 나비 판정에 들어가지 않는다. 무엇을 배웠는지를 보여줄 뿐, 믿을 수 있는지는 위의 검증 축이 답한다." 트러스트 미터 §9.2의 규칙(두 숫자가 서로 다른 말을 하면 사용자는 숫자를 믿는다)을 같은 방식으로 지킨다.
- 스토어 추가는 최소로 한다: 마지막 회고 시각 조회 하나. 나머지는 기존 읽기로 계산한다.

### 6.4 회고 트리거 확장 — 순수 대화 세션도 배운다

M8b가 남긴 공백(§5.6): 자율 행동이 없던 세션은 judge를 부르지 않아 기억 제안 기회가 없다. 확장 규칙은 이렇다.

> 사건이 없어도, 커서 이후 사용자 메시지가 `REFLECTION_MIN_USER_MESSAGES`(기본 2) 이상이면 기억 추출 전용으로 judge를 부른다.

한 줄짜리 세션("고마워")에 모델 호출을 붙이지 않기 위한 최소 문턱이다. 비용 상한은 §4.3의 스윕 상한(3세션)이 계속 지킨다.

### 6.5 검증 계획

- 스파이크 — 랭킹: 관련 기억이 무관 기억을 이기고 예산 안에 먼저 들어감, 동점 시 기존 순서 유지, `queryText` 부재 시 기존 정렬과 byte-for-byte 동일, 한글 토큰 매칭. 트리거: 사건 없는 세션이 문턱 이상이면 제안이 안착하고 미만이면 judge 무호출, 커서는 두 경우 모두 전진.
- 셸 — `learning` 블록 계산·노출, 패널 렌더 카피 테스트(growthCopy 패턴).
- 회귀 — M8a·M8b와 같은 전체 세트. 특히 주입 no-op 불변(spike:learn)과 M8a/M8b 스파이크 전부.

### 6.6 구현 상태 — ✅ 완료(2026-07-30)

신규 `npm run spike:rank` **13/13 PASS**, `npm run spike:reflection` **40/40 PASS**(두 드라이버, M8a·M8b 34건 포함), 회귀 spike 10종 전부 PASS(`spike:learn` 10/10 · `spike:growth` 22/22 · `spike:checkin` 10/10 · `spike:02` 5/5 · `spike:autonomy` 10/10 · `spike:p15` 11/11 · `spike:golden` 11/11 · `spike:bootstrap` 8/8 · `spike:export` 11/11 · `spike:import` 11/11), 셸 테스트 495/495, 타입체크 clean(양 트리, 기존 베이스라인 4건 제외), `build:app` exit 0. 구현하며 확정된 설계가 여섯 있다.

- **폴백이 조건문이 아니라 구조다.** "관련도가 도움이 되는가"를 판정하는 분기를 두지 않는다. `queryText`가 없으면 점수 맵이 비고, 어떤 후보도 겹치지 않으면 모든 조회가 같은 0을 돌려준다. 두 경우 모두 비교자의 첫 줄이 0이 되어 기존 scope→type→최신순으로 떨어진다. 분기가 없으므로 틀릴 분기도 없다. 스파이크는 M8c 이전 비교자를 **그대로 복사해** 60행 모집단(타임스탬프 충돌 포함)에서 순서가 글자 그대로 같음을 확인한다 — 새 코드가 자기 자신과 같은지 묻는 검사는 아무것도 증명하지 않는다.
- **한글 토큰은 먼저 울타리를 친다.** 정규식 한 줄에 `한글|일반문자` 교대를 쓰면 조용히 실패한다. `config파일`을 왼쪽부터 훑으면 `c`에서 한글 가지가 걸리지 않고 일반 문자 가지가 경계를 넘어 달려 `config파일` 한 토큰이 된다 — 양쪽 어디에도 매칭되지 않는다. 그래서 한글 런을 공백으로 감싼 뒤 분리한다. 스파이크가 이 실패를 실제로 잡았다.
- **정규화는 √(기억 토큰 수)로 나눈다.** 겹침 절대량만 쓰면 장황한 기억이 길다는 이유로 이기고, 전체 토큰 수로 나누면 주제를 제대로 덮은 긴 기억이 단어 하나 스친 짧은 기억에게 진다. Jaccard는 **질의 길이로도** 나누는데 그 인수는 모든 후보에 같이 걸리므로 순서를 바꾸지 못한다 — 여기서는 사는 것이 없다.
- **예산 검증은 예산을 손으로 적으면 안 된다.** 선택은 greedy라, 관련 기억의 줄이 손으로 고른 예산보다 길면 그것이 탈락하고 짧은 무관 기억이 들어간다. 검사는 통과하는 것처럼 보이면서 실제로는 **줄 길이를 재고 있다.** 그래서 스파이크는 예산을 렌더된 줄에서 계산한다.
- **`queryText`는 runTurn이 `userText`로 기본값을 잡지 않는다.** 자율 실행 2단계 이후의 `userText`는 하네스의 "계속하라" 프롬프트라 사용자가 원하는 것을 말해 주지 않는다. 셸이 `turnText`(멘션이 벗겨진 실제 과업 텍스트)를 모든 단계에 넘긴다. 기본값을 두지 않은 덕에 기존 호출자와 기존 스파이크는 이 필드의 존재로 아무것도 바뀌지 않는다.
- **학습 블록은 `GrowthReport` 밖에 있다.** 같은 응답의 **형제 필드**이지 안의 필드가 아니다. 트러스트 미터 §2(개수는 신뢰가 아니다)와 §9.2 규칙 2(두 숫자가 다른 말을 하면 안 된다)를 오래 지키는 방법은 문구가 아니라 **타입**이다 — 미터의 모양에 그 필드들이 아예 없으면 흘러들 수 없다. API 테스트가 `growth`에 학습 카운트가 없음을 직접 확인한다. 패널은 그 위에 문장을 얹는다("이 숫자는 나비 판정에 들어가지 않는다").

미검증으로 남는 것 — 어휘 점수의 **실사용 품질**이다. 스파이크는 랭킹이 결정론적이고, 관련 기억이 예산을 이기고, 신호가 없을 때 기존 순서가 보존됨을 증명하지만, 실제 대화에서 형태소가 다른 한국어(`실행`/`실행한다`)나 동의어를 놓치는 빈도는 재지 않는다. §8의 임베딩 판단은 이 실측 뒤로 남는다. 또한 라이브 모델이 사건 없는 세션에서 뽑는 기억 후보의 품질도 mock으로는 증명되지 않는다.
